# Research & Technical Decisions: Negative Authentication Test Cases (401/403)

**Feature Branch**: `007-negative-auth-tests`
**Date**: 2026-09-20
**Status**: Completed

## 1. Negative Authentication Generation Architecture

### Decision: In-Memory Algorithmic Mutation via Generator Submodule
- **Decision**: Implement negative authentication test case generation as a pure, deterministic in-memory transformation in `src/specprobe/generator/negative_auth.py`, deriving 401 and 403 test cases directly from the validated happy-path `GeneratedTestCase` and `OperationChunk` security metadata.
- **Rationale**:
  - Adheres strictly to Constitution Principle II (Deterministic Artifact Generation / Zero-LLM). Synthesizing negative authentication tests requires no semantic judgment or probabilistic inference—it is a purely deterministic transformation of the happy-path fixture (stripping headers/query tokens for 401, corrupting credentials for 403).
  - Preserves the realistic path parameters, headers, and request body generated by the LLM for the happy path, ensuring negative test requests are syntactically valid HTTP requests that fail solely on authentication/authorization.
  - Zero token overhead and sub-millisecond execution latency per operation.
- **Alternatives Considered**:
  - *Separate LLM prompt for negative tests*: Rejected because probabilistic models introduce drift, hallucinated payloads, non-deterministic output, and 3x token/latency costs for an algorithmic task.
  - *Generating negative tests inside exporter only*: Rejected because downstream tools (such as `specprobe audit` or external test runners) need first-class access to negative test case records in JSONL streams.

## 2. Test Case Discriminator & Schema Compatibility

### Decision: First-Class `test_type` Field with Safe Default
- **Decision**: Extend `GeneratedTestCase` in `src/specprobe/generator/models.py` with `test_type: str = Field(default="positive", description="...")`.
  - Defined values:
    - `"positive"` (happy-path, 2xx success)
    - `"negative_auth_missing"` (401 Unauthorized, omitted credentials)
    - `"negative_auth_invalid"` (403 Forbidden, invalid credentials)
- **Rationale**:
  - Setting the default to `"positive"` guarantees 100% backward compatibility with all existing JSONL test case records, cached LLM responses, and golden test fixtures.
  - Downstream consumers (exporters, audit engine, CLI formatters) can unambiguously filter or format test cases without relying on brittle substring matching on `description` or heuristic checks on `response.status_code`.
- **Alternatives Considered**:
  - *Relying only on `response.status_code`*: Rejected because a 401 or 403 status code does not inherently indicate whether the test case was generated for missing credentials, invalid credentials, or application-level authorization failure.
  - *Subclassing `GeneratedTestCase` (e.g. `NegativeTestCase`)*: Rejected because JSONL streaming and pipeline serialization require a uniform schema model (Constitution Principle I: Clear Idiomatic Code Over Abstractions).

## 3. Credential Invalidation Strategy (403 Forbidden)

### Decision: Protocol-Valid Invalid Literal Strings
- **Decision**: Invalidate credentials using scheme-aware invalid literal values that maintain valid protocol syntax:
  - **HTTP Bearer & OAuth2**: `Authorization: Bearer invalid_token`
  - **HTTP Basic**: `Authorization: Basic aW52YWxpZDppbnZhbGlk` (base64 representation of `"invalid:invalid"`)
  - **API Key (Header)**: `<header_name>: invalid_<name>_key`
  - **API Key (Query)**: `<query_param>=invalid_<name>_key`
  - **Cookie**: `Cookie: <cookie_name>=invalid_<name>_token`
- **Rationale**:
  - Many HTTP servers and reverse proxies reject malformed `Authorization` headers (e.g. missing `Bearer ` prefix or invalid base64) with `400 Bad Request` before the request reaches the authentication/authorization layer. Emitting protocol-valid syntax guarantees the API server's authentication filter evaluates the token and responds with the intended `403 Forbidden` (or `401 Unauthorized`).
- **Alternatives Considered**:
  - *Universal `<invalid_credentials>` placeholder*: Rejected because raw angle-bracket strings in `Authorization` headers cause `400 Bad Request` on standard web servers.
  - *Randomized garbage strings*: Rejected because randomness violates Constitution Principle II (reproducibility and determinism).

## 4. Multi-Scheme & Alternative Handling (OR Logic)

### Decision: Target Primary Resolved Scheme for 403, Strip All for 401
- **Decision**:
  - For HTTP 401: Strip all authentication headers and query parameters corresponding to any declared security scheme in `chunk.metadata.security`.
  - For HTTP 403: Corrupt only the primary winning security scheme resolved by `SecurityResolver` (following Feature 006 precedence: Bearer/OAuth2 > apiKey header > apiKey query > Basic).
- **Rationale**:
  - For 401, any credential present on an endpoint with alternative schemes might grant access, so all credentials must be absent.
  - For 403, corrupting the primary scheme matches the happy path's selected scheme and prevents an exponential explosion of test cases when an operation defines 3 or 4 alternative schemes.
  - Produces a consistent 1:1:1 test case structure per secured operation: 1 happy path, 1 missing-auth (401), 1 invalid-auth (403).
- **Alternatives Considered**:
  - *Generate a 403 case for every alternative scheme*: Rejected because it multiplies test count without testing distinct server endpoints.

## 5. Exporter Representation & Variable Scoping

### Decision: Inline Invalid Literals on Requests & Sibling Folder Placement
- **Decision**:
  - **Postman**:
    - Placed as sibling requests in the operation's existing tag folder, named `[401] <Operation Title>` and `[403] <Operation Title>`.
    - 401 requests omit auth headers and query params entirely.
    - 403 requests embed inline invalid literal values directly in request headers/query params (e.g. `Bearer invalid_token`), without defining or referencing collection variables.
    - Collection variables are aggregated solely from `positive` test cases to prevent invalid tokens from leaking into collection defaults.
  - **REST Client (`.http`)**:
    - Labeled with `# @name <operation_id>_401` and `# @name <operation_id>_403`.
    - Document `# Expected Status: 401` and `# Expected Status: 403`.
    - 403 requests embed inline invalid literal values directly. Top-level file variables (`@<var>`) are aggregated solely from positive test cases.
- **Rationale**:
  - Keeps negative tests 100% self-contained and runnable out of the box. Users only need to set their real credentials in the top-level collection/file variables for happy-path tests, and negative tests will still pass against mock or test servers without conflicting.
  - Sibling placement in Postman keeps all test variants for an operation co-located without deep folder hierarchy.
- **Alternatives Considered**:
  - *Generating separate invalid variables like `{{bearerAuth_invalid}}`*: Rejected because it forces users to manage double the variables for no benefit.
  - *Creating separate top-level folders in Postman*: Rejected because it fragments tests for a single endpoint across multiple directories.

## 6. CLI Flag Design & Defaults

### Decision: Enabled by Default with `--no-negative-auth` Opt-Out
- **Decision**: In `src/specprobe/cli.py`, add `@click.option("--negative-auth/--no-negative-auth", default=True, ...)` to `specprobe generate`.
- **Rationale**:
  - Out of the box, `specprobe generate` delivers complete test suites (happy path + auth rejection baselines) without requiring the user to look up extra flags.
  - Users who only want happy-path test cases can cleanly opt out using `--no-negative-auth`.
- **Alternatives Considered**:
  - *Disabled by default with `--negative-auth`*: Rejected because automated security testing is a primary goal of SpecProbe, and sensible defaults reduce user friction.

# Research & Technical Decisions: Minimal Local Mock Server (`specprobe mock`)

**Feature**: `011-mock-server` | **Date**: 2026-09-22 | **Spec**: [spec.md](file:///C:/Users/mwalc/source/repos/specprobe/specs/011-mock-server/spec.md)

---

## 1. HTTP Server Runtime: Standard Library `http.server.ThreadingHTTPServer`

### Decision
Use Python's built-in `http.server.ThreadingHTTPServer` combined with a custom `http.server.BaseHTTPRequestHandler` subclass.

### Rationale
- **Constitution Principle I (Clear Idiomatic Code Over Abstractions)**: Standard library `http.server` provides everything needed to bind a TCP socket, parse HTTP/1.1 requests, route methods, and write headers/bodies without introducing third-party framework overhead.
- **Zero New Dependencies**: Avoids adding heavy async or ASGI frameworks (`starlette`, `fastapi`, `uvicorn`, `anyio`, `h11`) to `pyproject.toml`.
- **Concurrent Request Handling**: `ThreadingHTTPServer` (added in Python 3.7) dispatches each incoming client connection to a separate thread. This ensures that test runners executing concurrent requests (e.g. Postman Collection Runner, Newman, or parallel HTTP calls) are serviced concurrently without head-of-line blocking.
- **Clean Socket Re-use**: Setting `allow_reuse_address = True` on the server guarantees immediate socket reclamation upon shutdown, preventing `OSError: [Errno 98] Address already in use` or Windows socket lingering during rapid test restarts.

### Alternatives Considered
- **`wsgiref.simple_server`**: Single-threaded by default, requires WSGI callable boilerplate and middleware layers for simple route dispatch, and has poor connection lifecycle management.
- **`starlette` / `uvicorn`**: Modern and feature-rich, but pulls in ~10 transitive dependencies and requires an async event loop for what is fundamentally a static canned response server. Rejected per Principle I.
- **`flask` / `werkzeug`**: Adds unnecessary WSGI routing trees, request context locals, and dependencies. Rejected.

## 2. Route Matching & Parameter Resolution Strategy

### Decision
Resolve path parameters statically at fixture load time from `request.path` and `request.path_params` (e.g., path template `/pets/{petId}` with `{"petId": "42"}` resolves to `/pets/42`). Store registered routes in an in-memory dictionary keyed by `(normalized_method, normalized_path)`, where `normalized_path` strips trailing slashes (except root `/`).

### Rationale
- **Deterministic O(1) Lookup**: At runtime, each incoming request is matched with a single dictionary lookup: `routes.get((method, path))`.
- **Strict Method + Path Matching**: Ignores incoming request headers, query parameters, and request bodies. This aligns directly with the user's requirements and prevents client-specific headers (e.g. `User-Agent`, auth credentials, header casing) from breaking test execution.
- **Full Pipeline Alignment**: Test fixtures generated by `specprobe generate` contain the concrete parameter values that were serialized into Postman collection URLs and `.http` files by `specprobe export`. Consequently, the exported requests will match the resolved path fixtures byte-for-byte.
- **First-Match Precedence**: If multiple fixtures in the test cases file target the exact same method and resolved path, the first matching fixture is registered and an informational warning is logged.

### Alternatives Considered
- **Dynamic Regex Route Matching**: Compiling path templates into regular expressions at server startup and parsing variables dynamically per request. Rejected for v1: because test artifacts contain concrete values matching the generated fixtures, regex matching adds runtime complexity and introduces route ambiguity (e.g. `/pets/{id}` vs `/pets/{type}`) without functional benefit for canned testing.

## 3. Deterministic Response Body Synthesis from JSON Schema Draft 7

### Decision
Implement a recursive, zero-LLM schema synthesizer (`synthesize_sample_from_schema`) that deterministically generates minimal valid JSON data structures conforming to `response.schema_shape` (JSON Schema Draft 7). If an explicit `response.body` is present in the fixture record, use it directly. For HTTP 204 No Content or null/empty schemas, emit an empty body `b""`.

### Rationale
- **Guarantees Test Assertions Pass**: Exported Postman collections emit `pm.response.to.have.jsonSchema(schema)` tests. Generating responses that strictly conform to the schema guarantees that these assertions pass during local execution.
- **Constitution Principle II (Zero-LLM Determinism)**: The synthesis is 100% deterministic, offline, and instant (<1ms per schema).
- **Draft 7 Schema Type Mapping**:
  - `object`: Recursively generates required properties (or all defined properties if required is unspecified). Resolves local `$defs` / `definitions` references.
  - `array`: Emits a single-item array `[synthesize(items)]` (or `[]` if items is empty).
  - `string`: Uses first enum value if `enum` defined; format defaults for `date-time` (`"2026-09-22T00:00:00Z"`), `date` (`"2026-09-22"`), `uuid` (`"00000000-0000-0000-0000-000000000000"`); otherwise `"string"`.
  - `integer` / `number`: Uses first enum value if `enum` defined; `minimum` if specified; otherwise `1`.
  - `boolean`: `True`.
  - `null`: `None`.
  - `const`: Constant literal value.

### Alternatives Considered
- **`hypothesis-jsonschema`**: Powerful for property testing, but introduces randomized output (violating deterministic reproducibility) and brings heavy test dependencies into runtime packages.
- **Empty Object `{}`**: While trivial to implement, an empty dictionary fails Postman schema validations when `required` properties or array root types are declared.

## 4. Lifecycle & Graceful Shutdown

### Decision
Run the mock server as a foreground blocking process in the terminal. Register signal handlers for `SIGINT` (Ctrl+C) and `SIGTERM`. When triggered:
1. Signal the `ThreadingHTTPServer` to stop accepting new requests (`server.shutdown()`).
2. Close the listening socket (`server.server_close()`).
3. Print a clean exit message via `rich.console.Console`.
4. Exit cleanly with exit code 0.

### Rationale
- **No Orphan Sockets**: Proper socket cleanup ensures port 8000 (or custom port) is released immediately, allowing instant re-execution without port collisions.
- **Native OS Portability**: Handles `KeyboardInterrupt` on Windows (where POSIX signals are simulated) and `SIGTERM`/`SIGINT` on Unix identically.
- **Interactive Observability**: Running in the foreground allows developers to view startup banners and per-request access logs in real time.

## 5. Input Ingestion & Pipe Streaming

### Decision
Support both a positional file argument (`specprobe mock <path>`) and standard input via `-` (e.g. `cat cases.jsonl | specprobe mock -` or `specprobe generate ... | specprobe mock -`).
- When reading from stdin (`-`), buffer all JSONL records into memory until EOF before creating the server socket and entering the HTTP listener loop.
- Validate that all parsed lines conform to `GeneratedTestCase` (or parse with `model_validate_json`).
- Filter records: retain only positive test cases (`test_type == "positive"` or status < 400).
- Reject empty input or malformed JSONL with exit code 1 and descriptive `stderr` output.

## Summary of Technical Choices

| Component | Choice | Rationale |
|-----------|--------|-----------|
| HTTP Server | `http.server.ThreadingHTTPServer` | Standard library, multi-threaded, zero dependencies. |
| Router | `MockRouter` (dict lookup) | O(1) lookup on `(method, normalized_path)`, trailing slash strip. |
| Body Synth | `synthesize_sample_from_schema` | Deterministic Draft 7 mock generator, passes Postman assertions. |
| CLI Interface | `click` + `rich` | Foreground blocking command, startup route table, concise request logs. |
| Input Support | File path or `-` (stdin) | Buffers JSONL before binding socket, consistent with SpecProbe CLI. |
